# Baseline migration — production runbook

`20260802090000_baseline_pre_citizen_booking` replaces two migration folders
that could never be replayed from an empty database (`prisma migrate deploy`
against a fresh DB failed with `P1014: the underlying table for model
EventSubmission does not exist`, because most of this project's schema was
applied via `prisma db push` and hand-written SQL in
`prisma/migrations_manual/`, not through `prisma migrate`).

This was verified safe against the local dev database (`moc_cms`): the
baseline SQL was generated by introspecting that database directly, applied
successfully to an empty database, and diffed back against `schema.prisma`
to confirm zero drift. See the comment block at the top of
`20260802090000_baseline_pre_citizen_booking/migration.sql` for the exact
commands used.

**This step could not be run against the production database from this
session — it requires SSH/DB access to the Plesk-hosted server that isn't
available here.** Before deploying the event-booking feature (or anything
that runs `prisma migrate deploy` from this branch), a human must do the
following on the production side:

## 1. Back up production

```bash
# On the server, or via a trusted admin connection:
pg_dump -U <user> -d <production_db> -F c -f "moc_cms_prod_$(date +%Y%m%d%H%M).dump"
```

Keep this dump somewhere safe until the deploy is confirmed good.

## 2. Check whether production already has this exact schema

If production has been kept in sync with the dev database the same way (via
`db push` + the files in `prisma/migrations_manual/`), it already has every
table and column this baseline describes, and must **not** have the baseline
SQL executed against it — that would fail on `CREATE TABLE` for tables that
already exist.

Verify first:

```bash
cd /var/www/vhosts/moc.gov.sy/httpdocs/next-app
npx prisma migrate status
```

- If it reports migrations from the old `20260714120000_business_logic_hardening`
  / `20260719113000_opera_event_sync` folders as applied, or reports schema
  drift, **stop and reconcile manually** — production's real history may
  differ from what this branch assumes. Do not proceed on assumption.
- If it reports the two old migrations as *not* applied (matching what this
  session found on the local dev DB) and the tables/columns clearly already
  exist (spot-check a few, e.g. `Event.bookingUrl`, `EventSubmission.dedupeKey`),
  proceed to step 3.

## 3. Mark the baseline as applied, without running it

```bash
npx prisma migrate resolve --applied 20260802090000_baseline_pre_citizen_booking
npx prisma migrate status
```

**This almost certainly will NOT yet report "up to date" — two more things
need cleanup, both discovered while doing this exact procedure against the
local dev DB:**

### 3a. A stale `_prisma_migrations` row

`resolve --applied` only *adds* a row for the new baseline; it does not
remove old rows for migrations whose folders were deleted. If production's
history has an old row like `20260714120000_business_logic_hardening` or
`20260719113000_opera_event_sync` sitting in `_prisma_migrations` from
before this baseline, `migrate status`/`migrate dev` will report it as
"applied to the database but missing from the local migrations directory."
Remove it (only after confirming in step 2 that its actual content is fully
subsumed by the baseline, which it is for those two specific names):

```sql
DELETE FROM "_prisma_migrations" WHERE migration_name = '20260714120000_business_logic_hardening';
DELETE FROM "_prisma_migrations" WHERE migration_name = '20260719113000_opera_event_sync';
```

### 3b. Real (harmless) schema drift on four `updatedAt` columns

`prisma migrate diff`'s introspection does not compare column defaults with
full fidelity in every case. Four columns —
`LegalLicenseApplication.updatedAt`, `LegalLicenseAttachment.updatedAt`,
`LegalLicenseFounder.updatedAt`, `LegalLicenseReviewItem.updatedAt` — were
found on the local dev DB to still carry a database-level `DEFAULT now()`
that `schema.prisma`'s `@updatedAt` does not declare (Prisma maintains this
column at the application layer on every write, so the DB default was never
functionally necessary, but its presence is still real drift). Run:

```sql
ALTER TABLE "LegalLicenseApplication" ALTER COLUMN "updatedAt" DROP DEFAULT;
ALTER TABLE "LegalLicenseAttachment" ALTER COLUMN "updatedAt" DROP DEFAULT;
ALTER TABLE "LegalLicenseFounder" ALTER COLUMN "updatedAt" DROP DEFAULT;
ALTER TABLE "LegalLicenseReviewItem" ALTER COLUMN "updatedAt" DROP DEFAULT;
```

Then confirm:

```bash
npx prisma migrate status   # should now report "Database schema is up to date!"
```

If it reports *any other* drift beyond these two known items, stop — that
means production's real schema history diverges from what this branch
assumes, and needs manual reconciliation before proceeding.

## 4. Only then deploy new migrations

Once `migrate status` is clean, `prisma migrate deploy` will apply only the
genuinely new migrations added on top of this baseline (the Task 4 feature
migration, etc.) — never the baseline itself.

## If production's schema does NOT already match

If step 2 shows production is missing tables/columns this baseline expects,
do not run `migrate resolve --applied`. Instead run the baseline SQL for
real (`npx prisma db execute --file
prisma/migrations/20260802090000_baseline_pre_citizen_booking/migration.sql`),
inside a transaction, against the **backed-up** database, and verify with
`migrate status` afterward.
